# ADR 0007：Attach 时诊断崩溃循环

- 状态：已接受
- 日期：2026-07-31

## 背景

使用 `restart: always` 或 `restart: on-failure` 的服务可能反复退出，大部分时间都在重启
退避中。Attach 此时只报告服务未运行，即使输出历史已经包含可能的原因。客户端需要可靠
的诊断，不能解析管理器错误字符串，也不应把服务列表变成通知系统。

## 决策

- 服务运行器按服务维护滚动 60 秒内存窗口，记录非成功退出以及 worker 启动或运行错误。
  三次失败会激活近期崩溃循环诊断。手动 stop/restart 路径不计入；普通管理器重启保留该
  窗口。
- 只有 attach 发现服务未运行时才检查警告。全局服务列表和 daemon 不主动发送新通知。
- 协议版本 5 增加 `Response::AttachUnavailable`，包含服务名、近期失败次数、窗口长度和
  可选的当前 `latest.log` 路径。普通 attach 错误仍使用 `Response::Error`。
- 只有当前运行确实启用了持久化时才返回日志路径。内存历史和持久化失败回退记录不会
  导出到临时文件。
- 交互式直接 attach 询问 `Open latest.log? [y/N]`。TUI 使用 `y` 或 `Enter` 打开，`n` 或
  `Esc` 取消。两者都使用 `$EDITOR`；attach 不增加编辑器选项。
- TUI 运行编辑器时离开 raw mode 和备用屏幕，编辑器结束后恢复并重绘。编辑器结束不会
  重试 attach，原来的 attach 操作仍然失败。非交互式 CLI 调用永远不询问。

## 结果

Attach 失败会解释常见的重启循环，并直接打开相关持久化输出，不会改变脚本行为。诊断只
表示近期状态，且是临时的；它不是健康模型、就绪检查或持久化失败计数器。使用内存历史
的服务仍需要通过 TUI 历史浏览器查看内容。
